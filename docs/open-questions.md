## 1. 別名の表に恒等写像を明示するか、それに伴い「書かれた写し先が常に勝つ」を降ろすか

**節: [10.1](roadmap.md#別名の表に恒等写像を明示する)。10.2 の着手前に決める。**

`title` / `date` のようにネイティブ名が well-known キーと一致するものを表に明示すると、
**表と `WellKnownMetadataMapper.Map` の挙動が食い違う。**

```csharp
a.Title = ["headline", MetadataAliasCandidate.Defaults];  // → ["headline", "title"]
```

```yaml
headline: A
title: B
```

`Map` は候補列を見る前に「写し先 `title` が書かれているか」を確かめて写しを打ち切るので、
`Title` は `B` になる。しかし利用者は `headline` を先に並べた。**表が優先順を宣言していても、
写し先自身の綴りだけは候補列の外側にある暗黙の第 0 位として振る舞う。**

### 決まっていないこと

- **(a) 恒等写像を普通の候補として扱い、暗黙の第 0 位を廃止する。**
  `Map` から「写し先が書かれていれば写さない」の分岐を落とし、
  `MetadataAliasTable.Set` から「写し先と同じ綴りの候補を落とす」も落とす。
  候補列がその写し先についての完全な真実になる

  代償: **利用者が恒等写像を書き忘れると、直接書いた値が別名に負ける。**
  `a.Description = ["abstract"]` と書いた利用者の文書に `description: X` と `abstract: Y` が
  あれば `Description` は `Y` になる。置き換えという演算の帰結としては正しいが、
  現在より鋭い。`MetadataAliasOptions` の doc に警告を書く必要がある

- **(b) 恒等写像を表に載せず、現状のまま暗黙の第 0 位を残す。**
  コード変更ゼロ。代償は表を読んでも語彙の全体が分からないこと
  （載っていない写し先が「一致するから省いた」のか「その形式には対応物が無い」のかが読めない）

- **(c) 恒等写像を表に載せるが、`Map` は現状のまま。** 表は文書として読めるようになるが、
  候補列に書いた順が効かない場合がある。**採らない**（表が嘘をつく）

### 材料

- **`title` の衝突は既に解けている。**（AsciiDoc の候補列を `[doctitle]` だけにする。
  [10.2 の該当節](roadmap.md#title-と-title-の衝突決定済み)）
  したがってこの項目は「表が読めるかどうか」だけの問題であり、機能上の必要はない
- **型で名前空間を分ける案（ソース空間とコア空間を別の型にする）も検討したが、
  投資に見合わない。** (a) が消す問題（暗黙の第 0 位、`Map` と `WithFallback` の順序依存）は
  親切診断を落とした後は「間違えても診断が出ない」だけで結果は変わらない。
  10.2 で AsciiDoc の語彙が実際に入ってから判断できる
- 決まれば `MarkdownAliasDefaults` の書き換え（慣行の借用 5 項目の削除、および (a) なら
  恒等写像 10 個の追加）が確定する。慣行の借用の削除だけはこの判断に依存しない

## 2. 再現可能ビルドの入力集合の定義

**節: [17.1](roadmap.md#171-docsarchitecturemd) と [9.5.1](roadmap.md#951-再現可能ビルドは-localremote-では決まらない)。**

roadmap は再現性（同一入力 → 同一出力）と再現可能ビルド（同一ソース ツリー → 同一出力）を
分けているが、**入力集合に何が入るのかを述べていない。** そこが決まらないと決められないこと:

- ファイルの mtime は**入力**なのか**環境**なのか。入力なら `git clone` した時刻で
  出力が変わるので再現可能ビルドではなくなる。環境なら mtime を出力に混ぜてはならない
- したがって **`:fileModTime` 相当の別名候補（Hugo の `lastmod` の暗黙のフォールバック）を
  そもそも許すのかどうか。** Hugo は `:git` / `:fileModTime` を並べるが、
  あれらは必ず値を返すので候補の順序が実際に効く
- ビルド時刻、ホスト名、絶対パス、ロケール、タイム ゾーンの扱い
  （`MetadataValue.TryGetDateTimeOffset` は既に `InvariantCulture` + UTC 既定で、
  この方向の判断を 1 つ済ませている）

**定義を書くのが先で、`:fileModTime` の可否はその帰結である。** 順序を逆にしてはならない。

### 材料 1: AdocNet の暗黙属性（項目 9 と共通）

AdocNet 1.0.22 は `Document.Attributes` に暗黙属性を 43 個入れ、うち 8 個
（`docdate` / `docdatetime` / `doctime` / `docyear` / `localdate` / `localdatetime` /
`localtime` / `localyear`）が**実行時の現在時刻**である。そのまま `MetadataValue` に流すと
同一ソース ツリーから同一出力が得られない。**ビルド時刻が入力なのか環境なのかが決まれば、
これらの扱いも決まる。**

### 材料 2: コマンドラインからのメタデータ上書き

Asciidoctor は `-a lang=ja` で文書内の代入に勝つ属性を、`-a lang=ja@` で負ける属性を渡せる。
Lithify に同じ口を設けるかどうかは**層の規則とは独立の問い**で、
再現可能ビルドの定義に直接触る。

- 再現可能ビルドの主張が「同一ソース ツリー → 同一出力」から
  「同一ソース ツリー **+ 同一コマンドライン** → 同一出力」に弱まる
- 現状 `RunLithifyAsync()` にメタデータを渡す口は無く、R5（サイトは C# で構成する）とも整合するので、
  **今は入れない。** 入れるとしたら入力集合の定義が済んだ後である
- なお強制の側（hard-set）は層では表せないが、**順序を逆にすれば表せる**
  （`siteOverrides.WithFallback(doc)`）。層に段を足す必要はない

## 3. `MetadataValue` を C# から組み立てる手段が無い

**節: [10.5](roadmap.md#105-lithifyblog) / [15](roadmap.md#15-samplesblog)。
10.5 の前提条件である（未決事項というより着手の障害）。**

**フォルダごとの既定値は最終的なキーを直接 C# で書くと決めた**（別名の写しを経ない。
既定値を書く場所には `ContentFormat` が無いので語彙の表を引けない）。
その決定により、この項目は 10.5 の着手前に片付いていなければならないものになった。

`MetadataValue` は構造だけを持つ閉じた DU なので、パーサーが組み立てるには足りているが、
**利用者が C# で書くには現実的でない**（サイトは C# で構成する。R5）。

```csharp
// Sequence: 冗長
new MetadataValue.Sequence([new MetadataValue.Scalar("tech"), new MetadataValue.Scalar("dotnet")])

// Mapping: 書けたものではない
new MetadataValue.Mapping(ImmutableDictionary.CreateRange(
    [KeyValuePair.Create(MetadataKey.Create("twitter"), (MetadataValue)new MetadataValue.Scalar("@x"))]))
```

必要そうなもの: `MetadataValue.Of(...)` 系のファクトリ、`string` からの暗黙の変換、
`Mapping` 用のコレクション式が通る形。**別名の設定とは独立した課題である**
（別名は `MetadataValue` を無変更で動かすだけなので、こちらの欠陥に影響されない）。

決めること: 暗黙の変換をどこまで入れるか（`Abstractions` の公開 API が増える）、
ディレクトリごとの既定値をどう書くか（`WithFallback` を外側から内側へ繰り返す形は決まっているが、
それを利用者がどう書くかは決まっていない）。

## 4. 別名の形式ごとの設定

**節: [10.1](roadmap.md#別名の設定101-の後に加えた設計)。当面は不要と判断したが、判断の根拠が経験ではなく調査である。**

現状は共通設定のみ。根拠だった「メタデータらしい属性は既存ジェネレーターと意味が一致する」は、
**語彙の互換を追わないと決めたことで論拠として使えなくなった**（既存ジェネレーターに
合わせないなら、意味が一致していることに意味が無い）。残る論拠は 2 つ:

- AsciiDoc の形式固有属性（`:toc:` / `:icons:` / `:imagesdir:` / `:stylesheet:`）は
  **描画指令**であって `WellKnownMetadata` に対応する写し先を持たない。
  形式によって同じ綴りが別の意味を持つ状況が、そもそも生じにくい
- 唯一見つかった実害候補（`title` の衝突）は形式ごとの設定では解決しなかった。
  **パーサーの既定を直すのが正しい直し方だった**（[10.2](roadmap.md#title-と-title-の衝突決定済み)）

**実例が出たら再考する。** 出たときに足すのは無害で、上書きが写し先ごとの置き換えなので
形式ごとの層は共通の層の後に同じ演算で重なるだけであり、既存の設定の意味は変わらない。

なお **`MetadataAliasOptions` そのものを撤去する案も検討したが、残す。** 語彙の互換を
追わない決定は Lithify が既定で何を受けるかの話であり、利用者が自分の横断語彙を作れること
（`a[MetadataKey.Create("meta-title")] = ["title"]`）は機能互換の側にある。

## 8. パスから導出するメタデータと、計算で決めるメタデータ

**節: [10.1](roadmap.md#別名の設定101-の後に加えた設計) の続き。別名の設定は「キー → キー」しか表せない。**

別名の設定を詰めるあいだ、考えていたのは `MetadataProvenance` でいう `Declared` と `Mapped`
ばかりだった。**`MetadataOrigin.Path` の側が手つかずである。**

- `MetadataOrigin.Path` は定義され、doc コメントは
  「ファイル名から導出した `WellKnownMetadata.Slug`」と
  「`posts/2026-01-01-hello.md` のような命名規則から取り出した日付」を名指ししている
- `MetadataProvenance.FromPath` も存在するが、**唯一の使用箇所は
  `WellKnownMetadataMapper.SetSourceFormat` の `source-format` の刻印だけ**である
- `WellKnownMetadata.Slug` の doc は「省略された場合はファイル名から導出される」と書いているが、
  **それを実装しているコードは無い**

**別名の表では構造的に表せない。** 表は写し先と候補の両方がキーであり、
値は `Entries` の別の項目から来る。パス由来の値はどのキーにも入っていないので、
`a.Slug = ["file-name"]` のような書き方は嘘になる（`file-name` という項目は存在しない）。

### 計算で決められるべきではないか

```csharp
a.Slug = context => GenerateSlug(context);
```

この形が要るのは確かで、`["a", "b"]` の候補列では表せないものが 2 つある。
**パス由来**（ファイル名、ディレクトリ、命名規則の日付）と、
**他の値からの計算**（`Title` を kebab-case にする）である。
Hugo の `:filename` / `:slug` / `:slugorfilename` のような番兵を候補列に混ぜる形もあるが、
それは `MetadataAliasCandidate.Defaults` を `":default"` という文字列にしなかったのと同じ理由で退ける
（同じ型の中の特定の綴りに特別な意味を割り当てると、実在しうるキー名と衝突する）。

決めること:

- **候補列と関数を同じスロットに置くのか、別のスロットにするのか。**
  同じなら「候補列 → どれも無ければ関数」という段になり、関数は
  `MetadataAliasTable`（キー → キーの純粋な値）には入らないので、
  別名の重ね合わせとは別の機構になる
- **`context` に何を渡すか。** パスは必須。ここで**他のメタデータを渡すと順序が問題になる**
  （`Slug` が `Title` を見るなら `Title` の解決が先でなければならず、
  相互参照が書ける形にすると循環しうる）。写しが写し先ごとに独立でいられるのは
  候補列がキー → キーだからである
- **出所は何になるか。** パスしか見ない関数なら `Path`、他の値を見るなら `Derived` に近いが、
  どちらも「利用者が書いた関数」であることは表せない。
  `MetadataOrigin` に分類を足すかどうか
- **再現性。** 関数が環境（時刻、環境変数）を読めると再現可能ビルドが壊れる。
  項目 2 の入力集合の定義と直結する
- **Slug の既定は関数の枠組みが要るのか。** 「ファイル名から導出」は仕様として固定でよいなら、
  利用者の関数とは別に**パーサーまたはビルド側の既定の導出**として実装できる。
  枠組みを先に作るか、既定の導出を先に作るかで順序が変わる

## 9. AdocNet の暗黙属性 43 個をどう扱うか

**節: [10.2](roadmap.md#未決-暗黙属性-43-個をどう扱うか)。10.2 の着手時に決める。**

AdocNet 1.0.22 は `Document.Attributes` に暗黙属性を 43 個入れる。
`Document.Attributes` は**宣言（`:name: value`）とエンジンが合成した暗黙属性を区別せず、
印も持たない。** そのまま `MetadataValue` に流すと 2 つ問題がある。

- **再現可能ビルドが壊れる。** 時刻由来の 8 個（`docdate` / `docdatetime` / `doctime` /
  `docyear` / `localdate` / `localdatetime` / `localtime` / `localyear`）が毎回変わる
- **`Entries` が 43 個で埋まる。** テンプレートがネイティブ綴りを直接読む経路
  （エスケープハッチ）の見通しが悪くなり、利用者が書いたものとエンジンが足したものが混ざる

候補:

- **既知の暗黙属性名の除外リスト**で落とす。AdocNet を更新すると増えた分が漏れる
- **許可リスト**で宣言相当のものだけ通す。仕様に載っている属性名を列挙する形になる
- **文書のテキストを走査して `:name:` の行があるものだけ通す。** 宣言かどうかを直接判定できるが、
  パーサーが AST の外側でテキストを見ることになり、AdocNet に読ませた意味が薄れる。
  `:name!:`（無効化）や属性の継続行の扱いも自分で書くことになる

決めること: **どの候補を採るか**と、**それが「AdocNet の非準拠部分は対応しない」という
方針に触らないか**（これはエンジンの欠落を補うのではなく、エンジンが渡してくるものを
選別する話なので、性質としては別である）。項目 2 の入力集合の定義と直結する。

## 10. 任意のタクソノミー

**節: [10.5](roadmap.md#105-lithifyblog)。10.5 が答えていない。**

Hugo は任意の分類軸を持てる（`categories` / `series` / 利用者が定義したもの）が、
**Lithify は `WellKnownMetadata.Tags` の 1 軸しか持たない。**
10.1 で「Hugo の `categories` は `tags` と別軸だから写さない」と決めたが、
**では別軸をどう表すのかは決めていない。**

「Hugo ではできたあれが Lithify ではできない」に該当するので、
[基本的には潰す対象](roadmap.md#語彙の互換は追わない機能の互換は基本的に潰す)である。
ただし語彙の話ではなく機能の話なので、判定の 3 つ（不変条件と衝突しないか /
既にある機構で表せないか / 出力形式に依存しないか）を通す必要がある。

決めること:

- **`WellKnownMetadata` に軸を増やすのか、軸の集合を利用者が定義する機構にするのか。**
  前者は Lithify が軸を決めることになり任意性が無い。後者は
  `WellKnownMetadata.Tags` が特別扱いされる理由を説明しなければならない
- **`WithTags()` はタグ一覧ページの生成まで含む。** 軸を増やすとページ生成の側も
  一般化が要る（出力パスの規則、一覧ページのテンプレート名、フィードを出すかどうか）
- **軸ごとの値の正規化。** タグの大文字小文字や空白の扱いは軸ごとに違いうる
  （`tags` は正規化したいが `series` は原文のままにしたい、など）
